# План дій: Мапінг сегментів "Огляду Верховного суду" до категорій класифікатора

Цей документ описує покроковий процес автоматизованого зв'язування розрізнених сегментів текстів судової практики із існуючим деревом категорій (вузлів) класифікатора `codification`.

## Етап 1: Підготовка даних та інфраструктури
1. **Аналіз структури даних сегментів:**
   - Зрозуміти, в якому форматі зараз зберігаються сегменти Огляду Верховного суду (CSV, JSON, окрема SQLite база чи текстові файли).
   - Визначити структуру таблиці для збереження результатів (додати поля `category_id`, `confidence_score`, `llm_reasoning` до таблиці сегментів).
2. **Вибір моделей:**
   - **Модель ембеддінгів / Пошуку:** Ми можемо використати вбудований у вашу SQLite базу FTS5 (повнотекстовий пошук) для первинного відбору, або локальну `sentence-transformers/paraphrase-multilingual-mpnet-base-v2` для векторів.
   - **LLM для фінального рішення:** Я (ваш поточний ШІ-асистент). Ви можете або надати мені файл із сегментами прямо тут у чаті, і я сам їх проаналізую та розмічу, або ми напишемо скрипт, який використовуватиме Gemini API.

## Етап 2: Побудова векторної бази (Семантичний індекс)
1. **Витяг категорій:** Написати запит до SQLite бази `codification` для отримання всіх 1,043 вузлів (ідентифікатор, назва, "текст для ембеддінгів").
2. **Генерація векторів категорій:** Пропустити тексти категорій через обрану модель ембеддінгів.
3. **Збереження індексу:** Зберегти згенеровані вектори у легковику векторну базу даних. Оскільки записів трохи більше тисячі, підійдуть локальні рішення на кшталт `FAISS`, `ChromaDB` або просто масиви `NumPy`.

## Етап 3: Алгоритм класифікації сегменту
Розробка Python-функції (скрипта), яка прийматиме 1 сегмент тексту і виконуватиме наступне:
1. **Векторизація сегменту:** Перетворення тексту сегмента судової практики на вектор.
2. **Пошук найближчих сусідів (KNN):** Порівняння вектора сегменту з індексом категорій та вибір Топ-5 (або Топ-10) найбільш схожих вузлів.
3. **Промпт для LLM:** Формування запиту до мовної моделі. 
   - *Контекст:* Текст сегменту.
   - *Варіанти:* Назви та описи Топ-5 знайдених категорій.
   - *Завдання:* Вибрати єдину найбільш релевантну категорію (або повернути "Немає підходящої", якщо жодна не підходить) та надати 1-2 речення аргументації.
4. **Парсинг відповіді:** Витягування з відповіді LLM ідентифікатора категорії (`category_id`).

## Етап 4: Масова обробка (Пайплайн)
1. **Написання скрипта-обробника (`mapper.py`):**
   - Завантаження всіх нерозмічених сегментів з джерела.
   - Запуск їх через алгоритм класифікації з Етапу 3.
   - Збереження результатів у базу (ID сегмента, ID призначеної категорії, аргументація LLM).
2. **Обробка помилок та Rate Limits:** Додавання пауз (sleep) та повторних спроб (retries) на випадок обмежень API (якщо використовуються хмарні моделі OpenAI/Anthropic/Google).

## Етап 5: Валідація та тестування
1. **Ручна перевірка (Семплювання):** Випадково вибрати 50-100 оброблених сегментів і вручну оцінити точність призначених категорій.
2. **Коригування промпту:** Якщо LLM часто помиляється між схожими категоріями, покращити промпт (додати правила відмінностей або приклади – Few-Shot Prompting).
3. **Оптимізація порогу:** Встановити мінімальний поріг схожості для семантичного пошуку (якщо жодна категорія не дотягує до порогу, навіть не відправляти в LLM, щоб економити ресурси).

## Етап 6: Інтеграція в користувацький інтерфейс (Відображення на екрані)
Цей етап дозволить бачити результати мапінгу прямо у веб-додатку.
1. **Оновлення HTML-шаблону (`public/index.html`):**
   - Додавання нової секції `<section class="segments-section">` (наприклад, "Судова практика / Огляд Верховного суду") одразу після блоків "Підрубрики" або "Семантичний контекст".
   - Створення базової структури для відображення карток сегментів (текст сегмента, бейдж впевненості ШІ, кнопка для показу аргументації вибору).
2. **Оновлення Backend (`server.py`):**
   - Розширення SQL-запитів в ендпоінті `/api/node/:code` (або створення нового `/api/node/:code/segments`), щоб разом із даними про категорію база повертала масив усіх прив'язаних до неї текстових сегментів.
3. **Оновлення Frontend логіки (`public/app.js`):**

   - Оновлення логіки відображення "Картки розділу": при кліку на гілку в дереві, якщо для неї є прив'язані сегменти з журналу, вони будуть динамічно відмальовуватись у новому блоці.
